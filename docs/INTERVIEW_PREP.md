## 1. Computer Vision Deep Dive

### Q: "Walk me through your detection pipeline."
**A:** 
1. **YOLOv8m** processes frames in batches of 4, filtering for class 0 (person) at confidence 0.35
2. Detections fed to **ByteTrack** — dual-threshold matching (high-conf first, then low-conf to recover lost tracks)
3. For each confirmed track, extract 256×128 crop → **OSNet** → 512-dim L2-normalised embedding
4. **Hybrid Re-ID** scores each track against known identities: `0.6×OSNet + 0.2×temporal + 0.2×trajectory`
5. **Shapely** zone classifier: foot position (bottom-centre of bbox) → polygon lookup → zone_id
6. **Event generator** emits typed events with UUID, session_id, sequence number, confidence score

### Q: "Why 0.35 confidence threshold for YOLO?"
**A:** Indoor CCTV has lower contrast and resolution than outdoor benchmarks. Default 0.5 threshold causes missed detections (persons behind glass, in shadows). 0.35 recovers ~15% more true positives with manageable false positive rate — ByteTrack's minimum 5-frame hit streak filters noise.

### Q: "How do you handle a customer who leaves and comes back?"
**A:** Re-entry detection in `reid_engine.py`:
- Gap 5-30 min → `detect_reentry()` returns True → `REENTRY` event emitted → new session_id created
- Gap < 5 min → treated as same session (brief exit, e.g., stepped outside)
- Gap > 30 min → beyond `reentry_window` → new identity (long absence = new visit context)

### Q: "What happens when two people occlude each other?"
**A:** ByteTrack's 90-frame lost-track buffer keeps the track alive during occlusion. When the person reappears, IoU matching reunites them with their track_id. If Re-ID fails (complete overlap), the Hybrid Re-ID's temporal + trajectory signals often recover the identity within 1-2 frames.

## 2. System Design Deep Dive

### Q: "Why pre-aggregate metrics? Why not compute on the fly?"
**A:** 
- A store open 12h generates ~2,000 events/day. Without pre-aggregation, every `/metrics` API call would `COUNT(DISTINCT session_id)` over potentially millions of rows.
- Pre-aggregation: `hourly_metrics` is upserted on every ingestion batch. API reads one indexed row.
- Tradeoff: slight write overhead (~5ms) vs massive read benefit (O(1) vs O(N) scans).
- Pattern is similar to materialized views, but we control update timing explicitly.

### Q: "How do you ensure idempotent event ingestion?"
**A:** 
- Every event has a UUID v4 `event_id` generated by the pipeline before DB insertion.
- `INSERT INTO events ... ON CONFLICT (event_id) DO NOTHING` — PostgreSQL handles dedup atomically.
- Batch can be safely retried on network failure — duplicate events silently discarded.
- API returns `{"ingested": N, "duplicates": M}` — caller knows exactly what happened.

### Q: "What if the pipeline crashes mid-video?"
**A:** 
- Video processor outputs `events.jsonl` as it runs (streaming write, not batch-at-end)
- On restart: re-run pipeline from beginning — duplicate events idempotently ignored
- Future improvement: checkpoint frame index → resume from last processed frame

## 3. Anomaly Detection

### Q: "How does Z-score anomaly detection work here?"
**A:**
```
z = (current_value - rolling_mean) / rolling_std
```
- Baseline: last 7 days, same hour-of-day (controls for daily traffic patterns)
- Threshold: |z| > 2.5 → anomaly (captures ~1.2% false positive rate)
- Severity: |z| > 3.0 = CRITICAL, > 2.8 = HIGH, > 2.5 = MEDIUM
- Requires minimum 3 data points; confidence auto-scales with data volume

### Q: "What if the store just opened? No baseline exists."
**A:** `_compute_zscore()` returns `None` if `len(historical) < 3`. No anomalies emitted during first 3 hours of operation. After 7 days, confidence reaches maximum. This is documented and communicated — better than false alarms on day 1.

## 4. AI Copilot

### Q: "How do you prevent GPT from hallucinating?"
**A:** Three-layer defence:
1. **System prompt** explicitly states: "Use ONLY the provided evidence. If insufficient, return INSUFFICIENT_DATA"
2. **Context grounding**: only retrieved DB metrics included — GPT cannot access external knowledge in the structured JSON context
3. **Post-validation**: `_validate_response()` checks observation count, `INSUFFICIENT_DATA` marker, auto-caps confidence if data_coverage < 2
Result: GPT acts as a reasoning engine over evidence, not a knowledge base.

### Q: "Why RAG and not fine-tuning?"
**A:** Store data changes every hour. A fine-tuned model would be stale by afternoon. RAG retrieves fresh metrics on every query — no retraining cost, always current. Fine-tuning is appropriate for teaching domain vocabulary, not for real-time data queries.

## 5. Scalability

### Q: "How would you scale this to 500 stores?"
**A (phased):**
- **Phase 1 (current):** Single PostgreSQL + 2 uvicorn workers handles ~50 stores
- **Phase 2 (100 stores):** Add PgBouncer connection pool + Redis cache for hot metrics
- **Phase 3 (500 stores):** Shard PostgreSQL by store_id prefix; async task queue (Celery+Redis) for video processing; CDN for video uploads
- **Only then:** Consider Kafka for event streaming (justified at ~100K events/hour+)
- Kubernetes stays off the table until Phase 3 — operational overhead not worth it earlier

### Q: "Why not Kafka for event streaming?"
**A:** A single store generates ~2,000 events/day = ~0.02 events/second. Kafka is designed for millions of messages/second. Using it here would be like using a freight train to deliver a pizza — massive operational overhead (Zookeeper/KRaft, consumer groups, partition management) with zero benefit. PostgreSQL with asyncpg handles our throughput with orders-of-magnitude headroom.
